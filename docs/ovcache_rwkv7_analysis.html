llama.cpp b10369OpenVINO 2026.2.1RWKV7ggml-backend复现确认

0. TL;DR

你那个报错 cache_r_l0 (view) (copy of ) ... OPENVINO0 ... CPY 已在本沙箱一字不差复现。本质是：llama.cpp 的 OpenVINO 后端对 RWKV7 的 recurrent state 支持不完整——state 张量被 pre-allocate 进 OpenVINO 设备 buffer 后，其 view/cpy 更新操作无法在 OpenVINO backend 上调度，ggml 的 scheduler 又不能把已分配的张量迁走，于是触发 GGML_ABORT 直接 coredump。

另外两点纠正：

  • cache.json（你说的 "ovcache"）跟这个 bug 无关，它是 OpenVINO GPU kernel 选择缓存，且和我们的 rwkv-openvino 项目机制完全不同（见 §4）。
  • OpenVINO backend 其实声明了 CPY 支持（ggml-decoder.cpp:339/1504 有 case GGML_OP_CPY），所以"OpenVINO 不支持 CPY"是误判；真正问题是 scheduler 在 RWKV7 state 场景下把 tensor 错误预分配到 OpenVINO buffer，而非后端缺算子。

2. 源码定位（根因）

报错出自 ggml/src/ggml-backend.cpp 的 ggml_backend_sched_backend_id_from_cur()：

if (tensor->buffer || (tensor->view_src && tensor->view_src->buffer)) {
    // since the tensor is pre-allocated, it cannot be moved to another backend
    ggml_backend_buffer_t buffer = tensor->view_src ? tensor->view_src->buffer : tensor->buffer;
    GGML_ABORT("pre-allocated tensor (%s) in a buffer (%s) that cannot run the operation (%s)",
               tensor->name, ggml_backend_buffer_name(buffer), ggml_op_name(tensor->op));
}

触发条件拆解：

条件本例取值含义
tensor->view_src 非空cache_r_l0 是 view 张量RWKV7 的 r-state 以 view 别名形式持久化
view_src->buffer 非空OPENVINO0state 的源张量已被 scheduler 预分配到 OpenVINO 设备 buffer
该 buffer 对应 backend 不能 run 此 opop=CPYggml_backend_sched_backend_from_buffer() 返回 -1
已 pre-alloc，无法迁移—进入 ABORT 分支 → 程序崩溃

RWKV7 的 state 在 llama.cpp 里的实现（src/models/rwkv7-base.cpp:107 → ggml/src/ggml.c:5849 ggml_rwkv_wkv7）：

// ggml.c:5849
struct ggml_tensor * ggml_rwkv_wkv7(ctx, ... struct ggml_tensor * state) {
    GGML_ASSERT(ggml_is_contiguous(state));
    // state 作为 src[6]，输出是 GGML_OP_RWKV_WKV7
    result->src[6] = state;
    result->op = GGML_OP_RWKV_WKV7;
}

RWKV7 的 recurrent state（cache_r_l0 / cache_k_l0 / cache_v_l0 …）是跨 token 持久张量，在 graph 里以 view/cpy 更新。启用 OpenVINO（-ngl 99）后，scheduler 把权重/激活都 offload 到 OpenVINO，state 张量也跟着被预分配进 OPENVINO0；但 state 的 view/cpy 写回路径在 RWKV7 场景下没被 OpenVINO backend 正确覆盖 → 调度死锁 → ABORT。

3. 为什么"和我们的 rwkv-openvino 不一样"

我们的项目根本不用 ggml 的多 backend scheduler：RWKV7 整个前向（含 state 递推）都在 OpenVINO IR 计算图内表达，state 作为图的 Parameter/Result 在图外管理（每步喂入/读出 numpy/OV tensor）。没有 "view tensor pre-allocated to a device buffer" 这个概念 → 天然没有这个 bug。已验证 GGUF K-quant → OV 原生压缩权重 bit-exact（Q4_K 非对称 u4 / Q6_K 对称 i8，max|err|≈1e-4 即 f16 舍入噪声）。

4. cache.json（ovcache）是什么，和我们的区别

维度llama.cpp 的 cache.json我们的 rwkv-openvino
层级OpenVINO GPU plugin 的 kernel 选择/二进制缓存（cl_cache 等价物）OpenVINO IR 模型 + 原生压缩权重（u4/i8 Constant）
内容CONVOLUTION / F16_BFYX_... 算子在不同数据布局下选哪个 GPU kernel 实现RWKV7 计算图（节点+权重），权重以压缩格式入图由 CPU/GPU/NPU 插件融合
作用加速 OpenVINO GPU 算子选择的自动调优直接表达 RWKV7 前向，避免 ggml 调度
与本 bug 关系无关（删掉 cache.json 照样崩）机制上避开了本 bug
一句话：cache.json 是 OpenVINO 运行时的 GPU kernel 缓存，跟 llama.cpp 上层的 RWKV7 state 调度冲突是两条独立的事。它不是"和我们一样的缓存"。

5. 可行的绕行/解决方向

方案做法评估
A. 纯 CPU build 跑 RWKV7用非 openvino的 llama.cpp build（如 llama-bXXXX-bin-ubuntu-x64.tar.gz），llama-cli -ngl 0最稳；但本 openvino 包即使是 -ngl 0 也强制 OpenVINO，所以必须换包
B. 等 upstream 修复RWKV7+OpenVINO 是 arch/backend 组合缺陷，后续 llama.cpp 版本可能修 state 的 backend 分配被动，需跟踪 b10369 之后的 commit
C. 用我们的 rwkv-openvino基于已验证 bit-exact 的压缩权重，搭完整 RWKV7 OV 图，state 走 Parameter/Result推荐；彻底绕开 ggml scheduler 的坑，且能复用 OV 原生 int4/int8 内核

6. 下一步建议

  1. 短期：若只想在 llama.cpp 里跑 RWKV7，换非-openvino 的 CPU build（方案 A），别用这个 openvino 包跑 RWKV7。
  2. 中期：推进 rwkv-openvino 的完整 RWKV7 OV 图（方案 C）。GGUF K-quant 压缩权重继承已 bit-exact 验证通过，下一步是把 rwkv7_torch.py 的前向逐层用 build_compressed_weight 重写进 OV opset，验证 7.2B Q4 在 8GB 内跑通。
  3. 已交付：bit-exact 的 gguf_kquant_repack.py + gguf_to_ov_compressed.py 已 git push（commit abc604b），你现在 git pull 即可拿到。
