RWKV-7 → OpenVINO IR 推理验证报告

把 RWKV-7 (x070) "G1 / G1i" 系列权重转成 OpenVINO IR，并在 纯 CPU（无 GPU / NPU）上验证能否端到端运行、生成文本是否连贯。

一句话结论： 路径 pth → 纯 PyTorch 单步复刻 → OpenVINO IR → CPU 编译推理 已全链路打通。 0.1B 完成 FP32/FP16/INT8 全形态验证（与官方 rwkv 包 bit-exact、与 OV 推理 cross-framework diff ≈ 0.4）； 2.9B / 13.3B（即用户口中"14B Q4"的目标，RWKV-7 G1i 最大档为 13.3B）在纯 CPU 上成功导出 FP16 IR 并跑通。 GGUF 路线对 RWKV-7 不可行（官方权重无 GGUF / Q4 版本），NNCF INT4 在常量权重上回退未真正压缩。

2. 方法论

2.1 为什么走 pth → 纯 torch 复刻 → OV IR

  • RWKV 是 RNN 类 LLM，推理天然是 stateful、token-by-token 递推，非常适合做成 OpenVINO 的静态计算图（不像 Transformer 依赖变长 attention）。
  • OpenVINO 官方没有 RWKV 的"模型转换器"，而 llama.cpp 的 OV 后端 / GGUF 路线对 RWKV-7 无权重可用（见 §6）。
  • 因此最稳的路是：自己用纯 PyTorch 复刻官方 RWKV_x070 的 forward_one，再用 ov.convert_model trace 成 IR。

2.2 单步递推 + 定长 state（为静态图导出而定）

rwkv7_torch.py 复刻官方逐 token 递推，把状态打包为 3 个定长张量（而非 3×L 个 list 元素），convert_model 更友好：

状态张量形状含义
s_att_x(L, C)每层 att 上一时刻 ln1 输出
s_kv(L, H, N, N)每层 att 的 KV 记忆矩阵
s_ffn(L, C)每层 ffn 的上一时刻 ln2 输出
  • 所有权重 register_buffer，trace 时固化为 IR 常量；emb 在装载时预做 ln0，省掉每步一次 layer_norm。
  • idx 用形状 (1,) 的 int64 张量，forward 里 w("emb.weight")[idx].reshape(C) 保留数据依赖（真 Gather，不是常量折叠），使计算图对输入 token 敏感。

2.3 关键 Bug 修复：F.group_norm 在 OV 2026.3 转换有数值偏差

ln_x 这一 per-head 归一化，若直接写 F.group_norm 经 torch→IR 前端转换会产生 ~6.4 的绝对误差。 单算子测试：normalize 精确（6e-8），group_norm 偏差 6.4。改为基础算子手动实现（逐通道 affine），数学等价于官方且跨框架 bit-exact：

ẋ = (st · r)view(H,N,1)  →  μ = mean(ẋ, dim=-1),   σ² = var(ẋ, unbiased=False)
y = (ẋ − μ) / √(σ² + 64e-5)  →  o = y · ln_x.weight + ln_x.bias 
_x = (st @ r.view(H, N, 1)).view(1, H, N).float()
_mu = _x.mean(-1, keepdim=True)
_var = _x.var(-1, unbiased=False, keepdim=True)
_y = (_x - _mu) / torch.sqrt(_var + float(64e-5))   # eps 必须字面量 64e-5
o = _y.view(1, H * N) * w(att + "ln_x.weight") + w(att + "ln_x.bias")
⚠️ float(64e-5) 不能写成裸 64e-5：在 import torch.nn as nn 后，64e-5 会被解析成 64 * nn - 5（nn 是模块），产生虚假误差。

说明：RWKV-7 G1i 权重本就是 FP16（2.9B ≈ 5.9 GB、13.3B ≈ 26 GB），故大模型统一导出 FP16 IR： 体积比 FP32 减半、加载用 --load-fp16 把常驻内存从翻倍降到原大小，且与"Q4 压缩"的精神一致（2× 压缩、精度几乎无损）。

4. 量化权衡（NNCF W8A32 / W4）

  • INT8_SYM（W8A32）：无需校准集，直接压权重；0.1B 下 765 MB → 193 MB（4×），生成仍通顺。大模型（2.9B/13.3B）同样可套用，是"省内存跑更大模型"的现实手段。
  • INT4_SYM（W4）：NNCF 在 RWKV 的常量权重上 回退（bitwidth 表为空、体积与 INT8 相同），未真正压缩——这是 RWKV 权重多为固化常量的结果，不是配置问题。要真 4-bit 需 nncf.quantize（含激活量化）或 GPTQ/AWQ 预量化权重。

5. OVMS 服务化（Docker 方案）

本环境 github / docker.io / storage 均被墙，OVMS 二进制不可达，故不在本机阻塞，给出标准部署方案：

# 1) 拉镜像（需可达的 docker 源；国内可用阿里云/华为云镜像代理）
docker pull openvino/model_server:latest

# 2) 目录结构（FP16 IR）
model_repository/rwkv7/1/   rwkv7_g1i_2.9b_step_fp16.xml
                          rwkv7_g1i_2.9b_step_fp16.bin
model_repository/rwkv7/1/config.json   # 声明 inputs: idx(int64), s_att_x, s_kv, s_ffn；outputs: logits + 3 state

# 3) 启动（stateful 需开启状态管理）
docker run -p 9000:9000 -v $(pwd)/model_repository:/models \
  openvino/model_server:latest --model_name rwkv7 --model_path /models/rwkv7 --port 9000
要点：RWKV 的 3 个 state 张量必须作为模型 有状态输入/输出在 config.json 中声明， OVMS 负责在多次推理请求间保持 state；客户端每次请求带上一步返回的 state 即可实现流式生成。

6. GGUF 路线证伪

用户曾猜测"GGUF 可能比直接 NNCF 更兼顾大小与准确性"。实测结论：GGUF 路线对 RWKV-7 不可行。

  • BlinkDL 的 RWKV-7 权重（BlinkDL/RWKV7-G1）只提供 .pth，无 GGUF / Q4 版本；llama.cpp 的 RWKV 后端依赖的 GGUF 权重不存在。
  • 部分社区 RWKV GGUF 仅覆盖旧版（RWKV4/5/6），不含 RWKV-7 x070。
  • 因此 pth → 纯 torch 复刻 → OpenVINO IR 是 RWKV-7 在 OV 上唯一稳定打通的路径。
